Zoo Quest Blueprint

Turn a day at the zoo into an adventure. This document is the plan we build from: what the MVP is, what it deliberately is not, and how the pieces fit before any real code is written.

Version 0.1September 3, 2026Stack: Next.js · Django REST · PostgreSQLFictional test zoo: Cedar Hollow Zoo

Section 0

Read this first

The brief is strong. Before agreeing with all of it, here is what I pushed on, what I changed, and the decisions that shape everything below.

Six decisions that simplify the whole product

1 · QR codes are URLs, not codes

Every printed marker encodes https://play.zooquest.app/s/CHZ-GIRAFFE-001. That means the phone's built-in camera app does the scanning, the browser opens, and Zoo Quest handles it. No in-app camera permission, no scanner library fighting iOS Safari, no "allow camera?" prompt on a kid's first interaction. The in-app scanner still exists (for people already inside the app), but it is the secondary path. This one choice removes the biggest technical risk in the brief.

2 · "Choose Adventure" lists quests, not challenge types

The brief's screen 2 offers "Animal Hunt / Scavenger Hunt / Brain Challenge / Photo Safari." Those are mechanics. A kid does not want to pick a mechanic; they want a mission. The screen should offer the zoo's quests (Savanna Safari, Rainforest Adventure, Wildlife Detective), each mixing several mechanics. Plus a free-roam mode: scan anything, discover animals, earn XP, no quest required. Mechanics stay a content-design tool for the admin.

3 · Django Admin is the MVP admin dashboard

Building a custom React admin for animals, exhibits, challenges, quests and badges is roughly a third of the total project. Django Admin gives you all of it in a day, with inlines, filters and permissions. We dress it up (a modern admin theme, custom list displays, a QR sheet print action) and ship. The custom admin is the first thing we build when a real zoo is ready to pay, because then we know what they actually need.

4 · Photo challenges are honor-system in the MVP

Uploading photos means object storage, moderation, and photos of children on your server. That is a privacy and cost problem, not a fun problem. MVP: "Take a photo of an animal eating. Show your team. Tap Done." The photo lives on the family's phone where it belongs. Uploads come back when there is a reason for them (a photo wall, AI verification).

5 · One phone, one family, one session

A guest session is the family. No parent/child tree, no per-child profiles. The only optional input is a team name. This also keeps you clean on children's privacy law (COPPA): we never collect a name, email, or photo from anyone. Family member profiles are a NEXT feature and the schema leaves room for them.

6 · The map is a picture with pins

A static zoo map image with exhibit pins at percentage coordinates. Discovered pins light up. No tiles, no GPS, no map library. It answers "where haven't we been yet?", which is the only question the MVP map needs to answer.

Section A

Product architecture

Three surfaces, one backend, one database. The phone is a controller; the zoo is the game board; the server is the referee keeping score.

The pieces

Explorer app

What families use. Next.js (App Router), mobile-first, installable PWA but not pushed to install. Talks only to the public API with a guest token. Five screens matter: Quest, Challenge, Success, Map, Profile.

API

Django + Django REST Framework. Two audiences: /api/v1/ for guests (token auth, zoo-scoped) and later /api/v1/admin/ for the custom admin (session auth, staff membership). All game rules live here, never in the frontend.

Admin

Django Admin for MVP, themed with Unfold so it does not look like 2008. Includes a "Print QR sheet" action that renders every marker as a printable page. Custom React admin is NEXT.

Database

PostgreSQL. Four Django apps: tenants (zoos, staff), content (what a zoo authors), play (what a family does), analytics (events). Content is authored rarely and read constantly; play data is write-heavy and per-session.

Hosting recommendation

Vercel for the Next.js app (free tier is fine for a field test, deploys on push, handles the PWA correctly). Railway for Django and PostgreSQL in one project (about $5 to $10 a month at MVP traffic, one-click Postgres, no server management). Media files (animal images, zoo map) on Cloudflare R2 or Railway volumes; R2 has no egress fees and a generous free tier. Total MVP infrastructure: under $15 a month.

Why not a single box, or Docker on a VPS? You would spend the first two weekends on deployment instead of the game. Why not AWS? Same reason, multiplied. Move when a paying zoo makes you.

Where the game logic lives

Three server-side subsystems carry the whole product, and each is a small, testable Python module:

  • Scan resolver. Given a marker code and a guest token: find the marker, record the scan, award discovery XP if this animal is new for the session, and return which active challenges this scan just completed or unlocked.
  • Challenge verifiers. One class per challenge type (AnimalHuntVerifier, WhoAmIVerifier, ...) with a single verify(challenge, session, submission) → Result method. Adding a challenge type later means adding a class and a frontend component, nothing else.
  • Badge rule engine. After any XP event, evaluate every active badge rule the session has not yet earned. Rules are rule_type + rule_config JSON so the admin can invent badges without a deploy.

Section C

User flow

One family, one phone, first visit. Screen names in green are the routes from Section F.

1
Visitor enters the zoo
Sign at the entrance: "Turn today into an adventure. Scan to start." The marker is CHZ-BASECAMP-001.
2
Scans with the camera app
Phone opens play.zooquest.app/s/CHZ-BASECAMP-001. The app has no session yet, so it creates a guest token for Cedar Hollow, stores it, and records the scan. /s/[code]
3
Welcome
Full-bleed image, "ZOO QUEST. Your adventure starts here." Optional team name (skippable). One button: Start Exploring. Badge "First Steps" is quietly earned by the scan and shown after the first success, not here. /z/cedar-hollow

Chooses an adventure
Three quest cards: Savanna Safari (featured, 6 missions, about 55 min), Rainforest Adventure, Wildlife Detective. Plus "Just explore" which skips quests. Tap Savanna Safari → Start Quest. /z/cedar-hollow/quests

Active quest, mission 1 of 6
Mission card: "Find a Giraffe. Head to the African Savanna..." Hint button (tap to reveal). Progress bar 0/6. Big Scan button pinned to the bottom. The map tab shows the Savanna pin pulsing. /z/cedar-hollow/quest/savanna-safari
6
Walks to the giraffes, scans the rail marker
Either the camera app or the in-app scanner opens /s/CHZ-GIRAFFE-001. The scan resolver: new animal → +100 discovery XP; matches the active mission's accepted marker → mission complete, +50 XP; badge engine → "Giraffe Spotter" unlocked. /s/[code]
7

"MISSION COMPLETE! You found a giraffe!" XP counter rolls up +150, the giraffe fact appears ("its tongue is purple"), then the badge card slides in. One button: Next Mission. /z/cedar-hollow/success
8
Mission 2, right here
"Who Am I?" riddle about the giraffe. Four big answer buttons. Correct → +100 XP and the explanation. Wrong → gentle shake, "Try again," no XP penalty. Mission 3 is the observation challenge: a 30-second timer while the family actually watches, then "What are they doing?" Any answer completes it.
9
Continues exploring
Elephant hunt, conservation question, then the lion on the ridge. Every scan also fires "Discovered!" for any animal the family passes that is not in the quest, so wandering is rewarded too.
10
Completes the quest
Final mission scan → quest complete screen: "SAVANNA SCOUT. Quest Complete! +500 XP." Level-up to Animal Explorer plays here if the threshold is crossed. Two buttons: See My Badges, Next Adventure.
11
Profile at the car
Level, XP, 6 animals discovered, 6 challenges done, 3 badges, 2 quests still locked with "Come back and finish" on them. /z/cedar-hollow/profile

Return visitor and edge paths

  • Scan without a quest active: discovery XP, animal card, and a prompt: "This marker is part of Savanna Safari. Start it?"
  • Scan a marker already discovered: animal page opens, "Already discovered" tag, no XP, no error. Repeat scans are logged.
  • Scan the wrong animal during a hunt: still a discovery (+100 XP), then "Not the one you're looking for. Hint?" The mission stays open.
  • Dead signal at the rail: the app shell loads from cache, the scan request retries three times with a visible "Saving..." state, then offers "Try again" without losing the code.
  • Opens the app a week later, same phone: same token in storage, everything is still there. Different phone: starts fresh (resume codes are NEXT).

Section D

Database schema

Four Django apps. Content is what a zoo authors; play is what a family does. The line between them is the line between tenant configuration and user data, and it matters for analytics, backups and eventually billing.

How the tables relate

tenants.Zoo ──┬── StaffMembership ── auth.User
              │
              ├── content.Exhibit ──┬── Animal ──── Marker (QR)
              │                     └── Marker (exhibit-only, e.g. Base Camp)
              ├── content.Challenge ── accept_markers (M2M → Marker)
              ├── content.Quest ── QuestChallenge ── Challenge
              ├── content.Badge          content.Level
              │
              └── play.GuestSession ──┬── Scan ──────── Marker
                                      ├── Discovery ─── Animal
                                      ├── QuestProgress ── Quest
                                      ├── ChallengeAttempt ── Challenge
                                      ├── BadgeAward ── Badge
                                      └── XPEvent  (ledger: every XP change, with its source)
analytics.Event ── Zoo, GuestSession (screen views, heartbeats, funnels)

tenants

class Zoo(models.Model):
    name          = CharField(120)
    slug          = SlugField(unique=True)          # cedar-hollow → /z/cedar-hollow
    timezone      = CharField(64, default="UTC")
    logo          = ImageField(blank=True)
    map_image     = ImageField(blank=True)          # the static map behind the pins
    primary_color = CharField(7, default="#2F6B4F")
    settings      = JSONField(default=dict)         # discovery_xp, quest_complete_xp,
                                                    # xp_by_difficulty, repeat_scan_cooldown_minutes
    is_active     = BooleanField(default=True)
    created_at    = DateTimeField(auto_now_add=True)

class StaffMembership(models.Model):
    user = ForeignKey(User)   zoo = ForeignKey(Zoo)
    role = CharField(choices=[("owner","Owner"),("editor","Editor"),("viewer","Viewer")])
    class Meta: unique_together = [("user","zoo")]

A ZooScopedModel abstract base (with zoo = ForeignKey(Zoo) and a custom manager .for_zoo(zoo)) is inherited by every content and play model. That is the entire multi-tenancy layer for the MVP, and it is enough.

    emoji               = CharField(8, blank=True)          # 🦒 fallback icon
    fun_facts           = JSONField(default=list)           # ["...", "..."]

    conservation_info   = TextField(blank=True)

    TYPES = animal_hunt | scavenger | who_am_i | observation | photo | conservation
    DIFFICULTY = easy | medium | hard
    title, slug, prompt, hint (blank), explanation (blank)   # explanation = the learning beat
    challenge_type, difficulty
    xp_reward       = PositiveIntegerField()      # editable; seeded from Zoo.settings defaults
    animal          = ForeignKey(Animal, null=True)
    exhibit         = ForeignKey(Exhibit, null=True)
    accept_markers  = ManyToManyField(Marker, blank=True)   # which scans complete it
    config          = JSONField(default=dict)     # options, correct, timer_seconds,
                                                  # any_answer_correct, verification
    is_active       = BooleanField(default=True)

class Quest(ZooScopedModel):
    name, slug, description, cover_image
    xp_reward         = PositiveIntegerField(default=500)
    badge             = ForeignKey("Badge", null=True, blank=True)
    estimated_minutes = PositiveIntegerField(null=True)
    starts_at, ends_at = DateTimeField(null=True)  # seasonal quests later, same table
    is_active, is_featured, sort_order

class QuestChallenge(models.Model):               # ordered through-table
    quest = ForeignKey(Quest)   challenge = ForeignKey(Challenge)
    order = PositiveIntegerField()   is_final = BooleanField(default=False)
    class Meta: unique_together = [("quest","order")]

class Badge(ZooScopedModel):
    name, slug, description, icon (emoji), image
    RULES = scan_count | discover_animal | discover_count | exhibit_count
          | challenge_type_count | quest_complete
    rule_type   = CharField(choices=RULES)
    rule_config = JSONField(default=dict)         # {"count":5,"tag":"africa"} etc.
    xp_reward   = PositiveIntegerField(default=0)
    is_secret   = BooleanField(default=False)     # hidden until earned
    is_active   = BooleanField(default=True)

class Level(ZooScopedModel):
    number = PositiveIntegerField()   title = CharField(80)   xp_required = PositiveIntegerField()
    class Meta: unique_together = [("zoo","number")]

play

class GuestSession(ZooScopedModel):               # "the family"
    token        = UUIDField(default=uuid4, unique=True, editable=False)
    team_name    = CharField(40, blank=True)
    total_xp     = PositiveIntegerField(default=0)   # denormalized from XPEvent
    created_at   = DateTimeField(auto_now_add=True)

    session = ForeignKey(GuestSession)   marker = ForeignKey(Marker)
    scanned_at = DateTimeField(auto_now_add=True)
    RESULT = discovery | repeat | completed_challenge | inactive
    result  = CharField(choices=RESULT)   xp_awarded = PositiveIntegerField(default=0)

class Discovery(models.Model):
    session = ForeignKey(GuestSession)   animal = ForeignKey(Animal)
    marker  = ForeignKey(Marker)   discovered_at = DateTimeField(auto_now_add=True)
    class Meta: unique_together = [("session","animal")]     # the anti-farming rule

class QuestProgress(models.Model):
    session = ForeignKey(GuestSession)   quest = ForeignKey(Quest)
    STATUS = active | completed | abandoned
    status, started_at, completed_at
    class Meta: unique_together = [("session","quest")]

class ChallengeAttempt(models.Model):
    session   = ForeignKey(GuestSession)   challenge = ForeignKey(Challenge)
    quest_progress = ForeignKey(QuestProgress, null=True)   # None in free roam
    STATUS = in_progress | completed
    status, attempts = PositiveIntegerField(default=0)

class BadgeAward(models.Model):
    session = ForeignKey(GuestSession)   badge = ForeignKey(Badge)   awarded_at
    class Meta: unique_together = [("session","badge")]

class XPEvent(models.Model):                       # append-only ledger
    session = ForeignKey(GuestSession)   amount = IntegerField()
    SOURCE = discovery | challenge | quest | badge | adjustment
    source_type, source_id = PositiveIntegerField(null=True)

analytics

class Event(models.Model):
    zoo     = ForeignKey(Zoo)   session = ForeignKey(GuestSession, null=True)
    name    = CharField(60)     # screen_view, quest_started, hint_revealed, app_open, ...
    payload = JSONField(default=dict)
    created_at = DateTimeField(auto_now_add=True, db_index=True)

Most of the brief's analytics list falls out of the play tables directly (quests started and completed from QuestProgress, most popular animal from Discovery, least completed challenge from ChallengeAttempt, average XP from GuestSession.total_xp). Event exists for things the play tables cannot see: screen views, session length, where people drop off.

Why these choices

  • JSON config on Challenge instead of six sub-tables: each type needs different fields, the admin edits them as a form per type, and adding a seventh type costs zero migrations. Validation lives in the verifier class for that type.
  • accept_markers as many-to-many: "Find a reptile" is satisfied by two different markers. One field handles hunts, scavenger clues and location-locked quizzes.
  • An XP ledger plus a denormalized total: the ledger makes analytics, debugging and future "undo" trivial; the total keeps the profile screen a single row read.
  • Unique constraints as game rules: one discovery per animal, one completion per challenge, one award per badge. The database enforces anti-abuse so the code does not have to be clever.
  • Nothing about people: no names, emails, photos or device IDs beyond a random token. Children's privacy is handled by never collecting anything.

Section E

API plan

Public endpoints are few and fat: the frontend should be able to render any screen from one request. Guests authenticate with X-Guest-Token; staff with Django sessions.

Staff endpoints NEXT

Not built in the MVP; Django Admin covers them. When the React admin comes, it is a straightforward set of DRF ModelViewSets under /api/v1/admin/zoos/{zoo}/ for animals, exhibits, markers, challenges, quests, badges and levels, plus GET .../analytics/summary/?range=today|7d|30d returning the numbers from Section 17 of the brief. Permissions come from StaffMembership.role.

Cross-cutting rules

  • Every guest endpoint resolves the session from the token and refuses content from a different zoo than the session's. Cross-zoo scans return a friendly "This marker belongs to another zoo."
  • All writes are idempotent where a flaky network could double-fire: starting a quest twice, scanning twice, submitting a completed challenge again all return the current state rather than an error.
  • Responses include the updated totals so the client never has to make a second request to animate the XP bar.
  • DRF throttling on scan and submit (for example 30 a minute per token) is cheap insurance.

Section F

Next.js App Router, TypeScript, Tailwind for speed, and as few libraries as possible. The frontend renders state; it never decides game rules.

State management

Two layers, deliberately small. TanStack Query owns everything that comes from the server (profile, quests, map) with cache keys per zoo and per session; mutations like scan and submit update the profile cache from their response so the XP bar moves without a refetch. A tiny Zustand store owns the three things that are client-only: the guest token, the last result to celebrate (handed to the Success screen), and UI flags like "hint revealed." No Redux, no context spaghetti.

API communication

One api.ts wrapper around fetch: sets the base URL, attaches X-Guest-Token, parses errors into a typed ApiError, and retries idempotent POSTs (scan, start, submit) up to three times with backoff. Types are generated from the DRF OpenAPI schema (drf-spectacular → openapi-typescript) so the frontend cannot drift from the backend silently.

QR scanning

  • Primary: the phone's camera app reads the marker URL. Zero code on our side beyond the /s/[code] route.
  • Secondary: in-app scanner using the native BarcodeDetector API where available (Chrome on Android, recent Safari) and @zxing/browser as the fallback. Requests the camera only when the user taps Scan, never on load.
  • Tertiary: "Type the code" field showing the printed short code. Saves the day when a lens is smudged or a permission is denied.

PWA considerations

  • Manifest with name, icons, display: standalone, theme color. Uses Serwist for the service worker (the maintained successor to next-pwa).
  • Precache the app shell and static assets; network-first for API with a short cache fallback for GET endpoints (map, quests) so the app still renders in a dead zone.
  • No install prompt during the visit (Section 0, problem 2). A quiet "Add to home screen to keep your badges" appears on the profile screen only.
  • Images: animal photos served resized (Next <Image>), map image cached after first load.
  • Performance budget: first meaningful render under 2 seconds on a mid-range Android over 4G. Measure with Lighthouse from milestone 2 onward.

Visual direction (for the design phase)

Deep forest greens and night-sky navy as grounds, one warm signal color (ember amber) for XP and calls to action, off-white text. Condensed, confident display type for mission titles; a humanist sans for body. Photography-led cards, not illustrations. Motion budget: the success sequence gets the animation; everything else is instant. The target feeling is "expedition field kit," which an adult will hold without embarrassment and a nine-year-old will find exciting.

Section G

Admin dashboard

Django Admin, configured with care, is the MVP admin. It gets a zoo to a working, self-managed experience in week one and tells us what the custom admin needs to be.

The custom admin NEXT

When a real zoo is on board, the React admin replaces Django Admin screen by screen, highest-friction first (probably Quest building and the analytics dashboard). Same API (Section E), same permissions. Django Admin stays as the superuser back office forever; that is what it is good at.

Section H

Development roadmap

Seven milestones, each small enough to finish in a few focused sessions, each ending with something you can click. Estimates assume evenings and weekends.

M0

Foundation

1 weekend

Monorepo (apps/api, apps/web), Docker Compose for Postgres, Django project with the four apps and settings split (local / production), Next.js project with Tailwind, TypeScript and the route skeleton, GitHub Actions running tests and lint, deploy both to Railway and Vercel with a hello-world endpoint.

Done when: the live URL shows "Zoo Quest" and /api/v1/health/ returns 200 from production.
M1

Content backbone

1 week

All tenants and content models and migrations. Django Admin registered and themed, type-aware challenge form. Load the Cedar Hollow fixture. Read-only endpoints: quests, quest detail, map, animals. QR sheet print action.

Done when: you can edit Cedar Hollow in the admin, hit the quest list from the browser, and print a sheet of 11 QR codes.
M2

Scan loop

1 week

play models, guest token auth, POST /sessions, POST /scan with the scan resolver, XP ledger, GET /me. Frontend: /s/[code] landing, Welcome, a first-cut Success screen, Profile with XP and discovered animals. Unit tests on the resolver (new, repeat, inactive, wrong zoo).

Done when: scanning printed markers with a real phone awards XP once per animal and the profile updates. This is the first moment the product exists.
M3

Quests and challenges

1 to 2 weeks

Quest start / progress / completion, the six verifier classes, submit and hint endpoints, quest completion XP. Frontend: Choose Adventure, Active Quest, the four challenge components, Quest Complete screen. Tests for every verifier including wrong answers and repeat submissions.

Done when: you can complete Savanna Safari end to end on a phone using the printed markers around your house.
M4

Progression

1 week

Levels, badge rule engine (six rule types), BadgeAward, badges endpoint. Frontend: full Success sequence (XP counter, fact, badge unlock, level up), badge case on Profile, Map with discovered pins and active mission highlight, animal detail.

Done when: finishing a quest unlocks its badge with a celebration and the map shows where you have not been.
M5

Hardening and analytics

1 week

Service worker and manifest, retry and "Saving..." states, throttling, analytics events from the client, the admin analytics view, Lighthouse pass, contrast and tap-target audit in sunlight (literally: take it outside). Error pages that make sense to a parent.

Done when: the app survives airplane mode toggled mid-scan and the analytics view shows your own test sessions.
M6

Field test

1 day + review

Print Cedar Hollow markers, place them around a park or a real zoo with permission, run three to five families through it, watch silently, then read the analytics. Write down what confused people and what made a kid run. Decide the NEXT list from evidence, not from the brief.

Done when: you can answer the MVP question with something other than a guess.
Order matters

M2 before M3 is the important call. The scan loop alone (walk, scan, discover, XP) is a playable toy. If that is not fun on its own, quests will not save it, and you will have learned that in two weeks instead of six.
